# Bootstrap Plan — {{project.name}}

This document captures the **physical bring-up plan** for {{project.name}} — the engineering path from "the grammar and semantics documents are written" to "a v0.1 compiler exists on disk, runs the test corpus green, and a working programmer can `git clone` and produce a binary that prints `hello, world`". Where `LANGUAGE_GRAMMAR.md`, `SEMANTICS.md`, and `TYPE_SYSTEM.md` pin down *what* the language is, this document pins down *how it gets built the first time* — which host language hosts the bootstrap compiler, what subset of the spec ships in v0.1, when (or whether) self-hosting happens, how the test corpus is structured, and which artefact is canonical when the spec and the reference implementation disagree.

A bootstrap plan that is wrong in the small ways costs months of engineering and is fixable; a bootstrap plan that is wrong in the big ways (host language with the wrong ecosystem for compiler work, v0.1 subset that is unimplementable inside one human-readable codebase, self-hosting attempted before the language is stable enough to compile itself) can cost years and is sometimes terminal — the graveyard of unfinished programming languages is largely populated by projects that chose the wrong bootstrap path in month two and never recovered. The 2026 lesson, learned the expensive way by every modern compiler that shipped (Rust 2010-2015, Swift 2010-2014, Roc 2018-present, Gleam 2016-present, Zig 2015-present), is **start in a host language with first-class compiler-engineering tooling, ship a minimum viable subset early, defer self-hosting until the language has a real user base, and write the test corpus as you go — never as a retrofit**.

Seven sections are surfaced because each is an independent strategic decision with multi-year compounding effects. The implementation language locks in your contributor pool, your build-time error quality, and your IDE-grade incremental-compilation ceiling for the entire bootstrap era. The minimum viable subset determines whether v0.1 ships in six months or six years. The self-hosting trajectory determines whether {{project.name}} ever proves to itself that it can compile a real program. The test corpus determines whether bugs are found by users or by CI. The reference-implementation-vs-specification choice determines who the language belongs to politically — the spec authors or the compiler maintainers. Build + distribution determines whether installing {{project.name}} is `curl | sh` or a thirty-step adventure. Decide each axis deliberately, write the rationale below, and revisit when reality breaks one of the assumptions.

## 1. Implementation language for v0.1

Which language hosts the v0.1 bootstrap compiler?

- **Rust is the 2026 default.** The Rust compiler-engineering ecosystem matured into the dominant choice over the 2022-2026 window, driven by three structural advantages no competitor matches: (a) **parser-combinator quality** — `chumsky` (Núria Mladenova et al., v0.10 in 2025) is best-in-class for error recovery, with built-in support for the kind of "didn't expect `}` here — did you forget a `;` on the previous line?" diagnostics that modern users now demand as table stakes; `winnow` (v0.7, fork of `nom` with cleaner API) is the perf-critical choice when the parser is on the hot path; `lalrpop` is the production LR(1) generator when the grammar is genuinely LR. (b) **rust-analyzer techniques are public-domain knowledge** — the Salsa-based query-driven incremental-compilation architecture (see `TOOLCHAIN.md §7`) is documented, copyable, and proven at scale; building a new language with IDE-grade incremental responsiveness is now a matter of *applying* the playbook rather than inventing it. (c) **the contributor pool already speaks Rust for compiler work** — the people who would be willing to commit weekends to a new programming-language project are disproportionately Rust users in 2026, because Rust *is* where serious open-source compiler work happens. The cost is Rust's learning curve for first-time contributors, which is real but partly mitigated by the language's reputation as a CV-positive skill to learn.
- **OCaml + menhir** is the traditional alternative with deep PL-heritage credentials. OCaml hosted the original Rust compiler (2010-2011, before bootstrapping), F#, Hack, Coq, Flow, Reason, ReScript, and a long tail of academic compilers. `menhir` (Inria's François Pottier and Yann Régis-Gianas; the canonical reference manual was last revised 2026-02 by the Inria team) is the de-facto OCaml LR(1) parser generator with first-class error-message support, incremental-parsing APIs, and a 20-year track record across production compilers. OCaml's algebraic data types and exhaustive pattern matching are arguably the single best match in any mainstream language for the shape of a compiler IR — you write `match ast with | Add (l, r) -> ... | Mul (l, r) -> ... | Lit n -> ...` and the compiler tells you if you forgot a case. The cost is ecosystem mass — OCaml has roughly 1% of Rust's contributor pool in 2026, the package manager (`opam`) is functional but rough, and the LSP / IDE story is acceptable rather than excellent. **Pick OCaml when you have OCaml expertise on the team and value the type-system match for compiler internals over Rust's broader ecosystem.**
- **Haskell + megaparsec** is the academic / research-design choice. `megaparsec` (Mark Karpov et al., v9.x as of 2026) is the canonical parser-combinator library, with the same error-recovery quality as Rust's `chumsky` and the additional advantage of running inside Haskell's monadic effect system — which means the parser composes naturally with your name-resolution and type-inference monads in a way that Rust's borrow checker fights you on. GHC's optimisation pipeline produces fast compilers (the GHC compiler itself, written in Haskell, is one of the most aggressive optimising compilers in production). The cost is the Haskell learning curve (much steeper than Rust for a non-Haskell contributor), the smaller contributor pool, and the runtime-laziness pitfalls that bite compiler engineers writing performance-sensitive code. **Pick Haskell when the language being implemented is itself functional or research-oriented (you will use Haskell's higher-kinded types and effect tracking heavily) and when the team is already fluent.**
- **C / C++ with hand-rolled recursive descent.** Still seen in performance-paranoid projects (the C compilers, `tcc`, `chibicc`, parts of `zig`'s self-hosted compiler before bootstrap). Pays in raw control and zero-dependency builds; pays in correctness (every hand-written compiler in C has shipped buffer-overflow CVEs eventually) and in modern-IDE-tooling absence. **Avoid for greenfield work in 2026 unless the project is itself a C-class systems language with a "self-host as fast as possible" trajectory.**
- **Avoid TypeScript for compiler-internals work.** The JavaScript / TypeScript tooling ecosystem itself migrated to Rust over the 2024-2026 window — `oxc` (oxidation-compiler, Boshen et al., production at Shopify and others), `swc` (Donny Wong, Vercel-funded, production at Next.js), `biome` (Rust-written, the formatter / linter / bundler combo) all replaced their JS / TS predecessors with Rust implementations because Rust delivered 10-50× speedups and the JS ecosystem voted with its feet. Building a new language compiler in TypeScript in 2026 means writing the same code your users' tooling vendors have spent two years replacing — the performance ceiling is wrong, the parser-combinator ecosystem is thin, and the contributor signal you send ("we chose the language our competitors abandoned for compiler work") is bad. Acceptable only when the host language is itself the target (a TypeScript-hosted compiler for a JavaScript-targeting DSL), and even then `oxc`-style Rust hosting with TS-output is the stronger play.
- **Self-host from line one.** Romantic and almost always wrong — you cannot write a {{project.name}} compiler in {{project.name}} before {{project.name}} exists. The historical exceptions (PyPy bootstrapped from RPython, Forth's classical self-hosting story) are domain-specific and not transferable. Plan for self-hosting (§3) but do not start there.

State the choice explicitly, name the parser library (chumsky / menhir / megaparsec / hand-rolled), and write the rationale into ADR-NNN. Cross-link `LANGUAGE_GRAMMAR.md §3` (grammar-class commitment) — the grammar class constrains which parser libraries are usable (LL(*) → chumsky / megaparsec; LR(1) → menhir / lalrpop; PEG → pest, cherrytomato; hand-rolled recursive descent works for any LL grammar).

## 2. Minimum viable subset (v0.1 grammar + semantics)

Which features ship in v0.1, and which are deliberately deferred to v0.2+?

The v0.1 subset is the most strategically important decision in this document, because **what is in v0.1 is what users build their first programs against, and what is deferred to v0.2 is what users have to wait for**. Get this wrong by shipping too much and the v0.1 release slips by quarters; get it wrong by shipping too little and v0.1 is a toy that no one writes a real program in. The 2026 reference for "minimum viable subset done right" is **Roc** (Richard Feldman et al., 2018-present) — Roc's v0 shipped with integers, floats, strings, lists, records, tags, pattern matching, and lambdas as a complete functional core, deferred record-update syntax sugar, modules, and the platform / effect system to subsequent milestones, and produced a language a user could write real (small) programs in from month nine. **Zig** is the cautionary tale — Andrew Kelley's effort has been excellent and the language is brilliant, but eight years in (2015-2026, still pre-1.0) the v0 subset was too ambitious (compile-time evaluation across the full type system, async/await with structured concurrency, comptime-driven generic constraints) and the v1.0 timeline kept slipping. Both projects shipped great languages; Roc's bootstrap plan was the better one.

**In-scope for v0.1 (canonical small core):**

- **Lexical syntax and the core grammar** as committed in `LANGUAGE_GRAMMAR.md` — what `LANGUAGE_GRAMMAR.md §1` calls "tier 1 syntax" (identifiers, literals, operators, control flow, function definitions, top-level declarations). Defer tier-2 sugar (comprehensions, pattern-matching extensions, do-notation, async sugar) to v0.2.
- **Primitive types** as committed in `TYPE_SYSTEM.md` — integers, floats, booleans, strings, the unit type. Defer fancier numeric towers (rationals, bignums, decimal floats), Unicode segmentation utilities, and string-formatting DSLs to STDLIB v0.2.
- **One aggregate type** — either records / structs *or* tagged unions / sum types, not both. Pick the one the paradigm demands (functional → sum types first; imperative → records first). Defer the other to v0.2 with a clear migration plan for users who built v0.1 programs.
- **Functions, including closures if `SEMANTICS.md` chose lexical scoping.** First-class functions, recursive functions, mutual recursion (requires forward declarations or two-pass name resolution; commit to one). Defer higher-rank polymorphism, type-class / trait dispatch, and effect rows to v0.2.
- **A minimum viable type system** — exactly the subset committed in `TYPE_SYSTEM.md §"v0.1 commitment"`. If full type inference is the goal (Hindley-Milner, bidirectional, etc.), implement the monomorphic core in v0.1 and add polymorphism in v0.2 (the Roc / Elm play). If type checking only (no inference), commit to mandatory annotations everywhere in v0.1 (the early-Rust play).
- **One concrete evaluation strategy** committed by `SEMANTICS.md §1`. Tree-walking interpreter is the cheapest (1-2 engineer-months for a basic core); bytecode VM is the workhorse (3-6 engineer-months, the Roc / Elixir play); native codegen is the long-haul (12+ engineer-months minimum to anything usable, the Rust / Zig / Swift play). **Pick one and ship it; do not split engineering across two backends in v0.1.**

**Deliberately deferred to v0.2+:**

- **Modules, namespaces, and the import / package system** — controversial because it feels like a v0.1 essential. The Roc / Elm experience says otherwise: a single-file v0.1 with everything in one global scope is *survivable* for the first six months of dogfooding and lets the compiler authors iterate on semantics without paying the design cost of modules. Add modules in v0.2 once the in-language constructs they wrap have settled. The Zig experience is the cautionary tale on the other side — Zig shipped modules early, then re-designed them twice.
- **Generics / parametric polymorphism** unless the language is *centrally* polymorphic (Haskell, OCaml, F#). For an imperative or first-order language, defer to v0.2.
- **The standard library beyond a "prelude"** — `print`, basic arithmetic, the list / record operations needed by the test corpus. Everything else is `STDLIB.md` v0.2+ work.
- **Concurrency primitives.** Even if `SEMANTICS.md §6` committed to async / channels / actors, defer the implementation to v0.2 unless concurrency is core to the v0.1 demo programs.
- **Macros, metaprogramming, comptime evaluation.** Always v0.2+ work — these are second-order language features that depend on the first-order language being stable.
- **A package manager.** `TOOLCHAIN.md §6` may commit to one; v0.1 ships without it (vendor dependencies by file path). v0.2 introduces the package manager.
- **An LSP server beyond minimal diagnostics.** `TOOLCHAIN.md §4` may commit to LSP 3.17 full support; v0.1 ships hover + diagnostics at most. Full LSP is v0.3+ work.

**Write a v0.1 "hello, world" demo program** in this section — five to ten lines of {{project.name}} that exercises every v0.1 feature. The demo program is the acceptance criterion for "is v0.1 done?" — if it compiles and runs, v0.1 ships; if any feature it touches is unfinished, v0.1 is not done. This sounds trivial; in practice it is the single most useful forcing function for keeping the v0.1 scope honest.

## 3. Self-hosting trajectory

When (and whether) does the {{project.name}} compiler get rewritten in {{project.name}}?

- **Phase 1 — host-implementation (v0.1 through v0.x).** The compiler is written in the host language chosen in §1. This is where {{project.name}} *lives* for its first one-to-three years of existence. The bootstrap compiler is iterated on as the language evolves, accepting that every breaking change to the language is one compiler edit (not two). **Do not exit Phase 1 until the language is stable enough that you would publish a v1.0** — self-hosting before stability means every breaking language change becomes a chicken-and-egg bootstrap problem.
- **Phase 2 — compile-self (the bootstrap milestone).** A new compiler is written in {{project.name}} and compiled by the Phase-1 compiler. Both compilers exist; CI runs the Phase-1 compiler on the Phase-2 source and verifies the resulting binary produces bit-identical output to the Phase-1 compiler on a corpus of test programs (the **diff-test bootstrap proof**). The release artefact is now the Phase-2 self-hosted compiler; the Phase-1 compiler is kept around as a "verified seed" — anyone bootstrapping {{project.name}} from source on a new platform first builds Phase-1 (in the host language), then uses it to build Phase-2 (the actual release artefact). Rust's bootstrap chain (`rustc` builds a stage0 from a previous-release binary, then builds stage1 from stage0, then builds stage2 from stage1 and diff-checks stage1 vs stage2) is the canonical reference for this protocol. **Plan Phase 2 for the v1.0-to-v1.5 window** — early enough that the community sees the language compiling itself before v2.0, late enough that the language is stable.
- **Phase 3 — stdlib rewrite (the maturity milestone).** The standard library, originally written in the host language as foreign-function-interface bindings, is progressively rewritten in {{project.name}} itself. Each subsystem (collections, IO, networking, concurrency primitives) becomes a "we used to call libc; now we have our own implementation" story. This is multi-year work; Rust started in 2010 and `std::sync` had pieces still being rewritten from unsafe-blocks-around-libc as late as 2022. **Phase 3 is forever** — there is no "Phase 4". The benefit is that every line of `std` becomes a torture-test for the language: any feature too painful for the stdlib authors to use is a feature that needs language-level redesign.
- **Never self-host.** Legitimate choice for some classes of language. Configuration languages (YAML, TOML), query DSLs (most SQL dialects), and transpilers-to-host (TypeScript → JavaScript, Elm → JavaScript, ReScript → JavaScript) often never self-host — the compiler stays in the host language forever because it is structurally bound to the host's parsing / type-checking / codegen libraries. Acceptable for those classes; not acceptable for a general-purpose language that wants to be taken seriously.

**State the target phase milestones in semver terms.** Example: "Phase 1: v0.1 through v1.0. Phase 2 bootstrap proof: v1.5. Phase 3 begins: v2.0; expected to be ongoing for the project's lifetime." Cross-link `STABILITY_AND_RFC.md` — the stability commitments at v1.0 are what make Phase 2 *safe* to attempt.

## 4. Test corpus

How is correctness pinned down?

- **Language-specification test suite.** A curated corpus of {{project.name}} source files with expected outputs (or expected error messages). Every feature in `LANGUAGE_GRAMMAR.md`, `SEMANTICS.md`, and `TYPE_SYSTEM.md` has at least one positive test (correct usage produces correct result) and at least one negative test (incorrect usage produces a specific, named diagnostic). The 2026 reference is **the Rust `rustc` UI test suite** under `tests/ui/` — every `.rs` file has a paired `.stderr` file with the exact expected diagnostic output, byte-for-byte; a change in compiler diagnostics requires a `--bless` step that regenerates the `.stderr` files, which forces the maintainer to read the diff and consciously approve every change. Adopt this protocol from day one — your future self will be grateful that every compiler diagnostic change is gated by a human review.
- **Conformance tests.** When the specification (§5) is canonical, conformance tests verify that an implementation matches the spec. WebAssembly's `wabt`-driven conformance suite is the modern reference for "specification + conformance harness + multiple implementations". For a single-implementation language (which {{project.name}} will be for years), conformance and the UI suite are the same thing; for a multi-implementation language (Python with CPython / PyPy / Jython / IronPython, JavaScript with V8 / SpiderMonkey / JavaScriptCore), the conformance suite is the legal contract.
- **Fuzzing.** The compiler input is parsed source text — an adversarial domain for which fuzzing is the industry-standard answer. `cargo-fuzz` (Rust, on libFuzzer) and AFL++ are the 2026 production references. Wire fuzzing into CI from v0.1 — the parser is the most likely component to crash on adversarial input, and a crashing parser is a denial-of-service against any service that runs {{project.name}} code from untrusted sources (REPLs, online playgrounds, build servers). Aim for "zero crashes from fuzzing in 100M iterations" as the v1.0 release gate.
- **Snapshot / golden tests for compiler diagnostics.** Beyond the UI suite, snapshot tests for the formatter's output, the LSP's hover / completion responses, and the documentation generator's HTML output. `insta` (Rust) is the workhorse. Snapshot tests are easy to maintain (delete the snapshot, re-run, review the diff) and catch a class of regressions ("the formatter started emitting an extra newline after `if` blocks") that no other test catches.
- **Self-test on the compiler itself.** Once Phase 2 (§3) is reached, the test that the compiler can compile itself becomes a load-bearing CI gate. Add a "compile rustc with rustc" -equivalent CI job and never let it regress.
- **Property-based tests for the optimiser / IR.** Once the compiler has multiple IR passes, property-based tests of the form "for all valid programs, IR-pass-N produces semantically-equivalent IR" catch optimisation bugs that no example-based test ever finds. `proptest` (Rust) or QuickCheck (Haskell) integration; the GHC and rustc compiler test suites both rely on this technique.

**State the corpus directory layout** (`tests/ui/`, `tests/conformance/`, `tests/fuzz/`, `tests/snapshots/`), the test runner (`cargo test` if Rust-hosted; the build tool from `TOOLCHAIN.md §7` otherwise), the CI gate (must-pass jobs versus advisory jobs), and the "blessing" workflow for snapshot updates. Cross-link `TESTING_STRATEGY.md` for the general project-level testing policy that wraps this language-specific corpus.

## 5. Reference implementation vs specification — which is canonical?

When a working program compiles successfully but the spec says it should not (or vice versa), which artefact is wrong?

- **The specification is canonical (the WebAssembly model).** A formal-or-formal-adjacent specification document is the legal contract. Implementations are measured against the spec via the conformance suite (§4). If `rustc` and the WebAssembly spec disagree on the behaviour of `i32.div_s INT_MIN -1`, the spec wins; the implementation is buggy. This is the right choice for any language with multiple implementations (or aspirations to have them), or for any language that wants to be embedded into government / regulated environments where "the spec says X" is a legally-meaningful claim. Pays a high cost: writing and maintaining a formal specification is a multi-year multi-engineer effort (WebAssembly took roughly five years for v1.0); every language change requires a synchronised spec edit and conformance-suite update. **Pick this when {{project.name}} aspires to ISO / W3C / IETF standardisation, or when multiple competing implementations are a goal.**
- **The reference implementation is canonical (the Python model).** CPython is the spec — Python's "language reference" document is best-effort prose that has historically lagged the implementation by years on edge cases, and "what CPython does" is the operative semantics. Other implementations (PyPy, Jython, IronPython, MicroPython) tracked CPython's behaviour because that was the user-visible contract; when an alternative implementation differed from CPython, *it* was the one users called buggy, regardless of what the prose said. **Pick this when {{project.name}} has one implementation (which it will for years) and the cost of a formal spec is not justified.** Almost every modern language ships with the reference-implementation-is-canonical model — Go, Rust (modulo the ongoing Ferrocene formalisation effort), Swift, Kotlin, Elixir, Roc, Gleam.
- **Hybrid (the modern Rust model).** A reference implementation (`rustc`) is the de-facto canonical artefact, *and* a formal specification (Ferrocene Language Specification, AdaCore + Ferrous Systems, published 2023, ongoing) exists for regulated-industry users. When the spec and `rustc` disagree, the bug is in whichever is wrong (and historically the spec has been the one updated, since it is the newer artefact playing catch-up). Pays the cost of both approaches; buys the option-value of being usable in safety-critical contexts without paying the full standardisation overhead. **A v3.0+ aspiration; not a v0.1 concern.**

**State the choice and the operational consequence.** If reference-impl is canonical, the compiler maintainers have unilateral authority to change semantics (and the responsibility to write the changelog). If spec is canonical, semantic changes require an RFC process (cross-link `STABILITY_AND_RFC.md`) and the implementation is a follower not a leader. For v0.1 of essentially any new language, **reference-implementation-is-canonical is the right answer** — defer the spec to v2.0+ once the language has earned the right to be standardised.

## 6. Build + distribution

How does a user install and run {{project.name}}?

- **Single static binary.** The 2026 default for new languages. The compiler is a single executable file with zero runtime dependencies (statically links its own runtime, embeds the stdlib, no external `.so` / `.dll` files required). Users `curl -fsSL https://{{project.name}}.dev/install | sh` and have a working compiler in twelve seconds. Go pioneered this in 2009 (`go` binary, statically linked, GOOS / GOARCH cross-compilation built in); Rust catches up via `rustup` (which downloads a statically-linked `rustc` binary). The cost is binary size (Rust's `rustc` is ~100 MB; Go's compiler is ~15 MB) and the discipline required to keep dependencies out of the runtime; the benefit is installation simplicity that pays for itself a hundred times over in user-onboarding. **Ship single-static-binary from v0.1 if at all possible.**
- **Multi-platform from day one.** The release matrix is `{linux, macos, windows} × {x86_64, aarch64}` = 6 platform targets minimum in 2026. Add `linux/riscv64` if your community has signal that RISC-V matters to them (it does for some hardware / academic communities; it does not for most application-developer communities yet). FreeBSD if the BSD community is in your audience. WASI / WebAssembly if you want browser-based playground demos. Cross-compilation from one platform to all targets (Zig is the gold standard here; Rust gets there via `cargo zigbuild` or `cross`) is what makes the release matrix economical — without cross-compilation, you need a CI cluster with one builder per target, which is operationally expensive.
- **Language-server included in the toolchain.** The LSP server (`TOOLCHAIN.md §4`) ships as a subcommand of the compiler binary or as a sibling binary in the same distribution, *not* as a separate community project the user has to discover. `rust-analyzer` is bundled with `rustup` since 2022; Go's `gopls` is in `go install` reach; Elixir's `elixir-ls` ships with the language. The 2026 user expectation is "install the language → editor support works". Anything less than that is friction.
- **Package manager + registry.** Cross-link `TOOLCHAIN.md §6` — the package manager and registry decisions are made there; this section commits to *when* they ship. **Package manager in v0.2; registry in v0.3.** Both can be deferred past v0.1; the user can vendor dependencies by file path in v0.1.
- **Installer ergonomics.** `rustup` (Rust), `gvm` (Go), `mise` / `asdf` (multi-language version managers) are the 2026 references for "install version N of the language alongside version M". For a single-version language in v0.1, a `curl | sh` installer is sufficient; a per-version installer (`{{project.name}}up`) is a v0.3+ investment that becomes essential once the language has multiple stable releases in active use.
- **Editor extensions.** VS Code Marketplace extension at v0.1 (the largest editor market). `tree-sitter-{{project.name}}` grammar (cross-link `TOOLCHAIN.md §4`) at v0.1 so Neovim, Helix, Zed, and Emacs 29+ users get syntax highlighting automatically. JetBrains plugin at v0.5+ (the JetBrains plugin platform has a longer review cycle; not worth the v0.1 investment).
- **The reproducible-build story.** Mentioned in `TOOLCHAIN.md §7` (build tool); the distribution-side commitment is that the published binary on `{{project.name}}.dev/install` is built reproducibly in CI, signed (Sigstore / Cosign in 2026), and the build provenance is published (SLSA Level 3+ for any language targeting regulated industries by v2.0). **Aspirational for v0.1, mandatory for v1.0** if {{project.name}} aims at enterprise / regulated usage.

State the v0.1 release matrix, the installer command, the editor-extension targets, and the bundling commitment (compiler + LSP + stdlib in one tarball, or separate binaries?). Cross-link `RELEASE_PROCESS.md` for the operational workflow that produces these artefacts and `TOOLCHAIN.md §7` (build tool) for the cross-compilation mechanics.
