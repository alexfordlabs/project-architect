# Stability and RFC Process — {{project.name}}

This document captures the **social contract** that {{project.name}} makes with its users about *change* — what guarantees stability, what is allowed to break, how new features get proposed, who decides, and which tooling carries existing programs across the discontinuities. Where `LANGUAGE_GRAMMAR.md`, `SEMANTICS.md`, and `TYPE_SYSTEM.md` pin down what the language *is* on the day a release ships, and `BOOTSTRAP_PLAN.md` and `TOOLCHAIN.md` pin down *how* an implementation is built, this document pins down *how the language is allowed to evolve* — the answer to every "but won't my code break?" email, the answer to every "how do I propose a feature?" forum post, and the answer to every "who decides if we change this?" maintainer disagreement. The 2026 lesson, learned the expensive way by Python (2008-2020 Python 3 migration), the early Node.js / io.js fork (2014-2015), and the JavaScript Strict Mode rollout (2009-present), is **codify the change-policy *before* you need it** — by the time you have a population of programs that broke and a population of users angry that their programs broke, it is already too late to design the deprecation cycle that would have prevented the breakage. Rust's edition system (2018, 2021, 2024 — the latter stabilised February 2025 with the `cargo fix --edition` migration tool) is the 2026 reference for "language evolution that does not break existing programs", and is referenced throughout this document as the canonical model.

Seven sections are surfaced because each is an independent commitment with multi-year compounding effects. The versioning policy controls the *grammar* of the conversation with users about what they can expect from a release labelled `1.5.3`. The stability tiers control which features users may rely on in production code and which are experimental playgrounds with explicit "this may be removed" labels. The breaking-change policy controls the answer to "what happens to my existing programs on the day {{project.name}} 2.0 ships?". The RFC process controls how design ideas enter the language; the decision-making model controls who has the authority to accept or reject them. The backwards-compatibility tooling controls whether breaking changes are technically survivable for users with large codebases. Decide each axis deliberately, write the rationale below, and revisit when the language matures past the early-adopter phase into the production-user phase — typically around v1.0, sometimes earlier if {{project.name}} attracts production users before the v1.0 release.

## 1. Versioning policy

How does {{project.name}} number its releases, and what do the numbers *mean*?

- **Semver (the modern default).** Major.Minor.Patch — `MAJOR` increments allow breaking changes, `MINOR` increments add backwards-compatible features, `PATCH` increments are bug-fix-only. The semver.org specification (Tom Preston-Werner et al., v2.0.0 as of 2026, unchanged since 2013) is the legal contract every modern package manager (Cargo, npm, pip / PEP 440, Go modules, Hex) enforces with version-resolution semantics. Semver is the 2026 default for nearly every new language because the tooling ecosystem assumes it — your package manager (`TOOLCHAIN.md §6`) parses semver constraints and resolves dependency graphs against them; deviating from semver is deviating from the ecosystem. The cost is the *MAJOR-increment-is-a-promise-of-breakage* implication: shipping v2.0.0 of {{project.name}} announces to the world "your v1.x code may not work", and the ecosystem reacts accordingly (long upgrade tails, version pinning, the lasting damage Python suffered from the 3.0 release). **Pick semver when {{project.name}} is a general-purpose language with a package-manager ecosystem and users who consume releases via that ecosystem.**
- **Edition-based versioning (the Rust 2024 model).** The compiler ships continuously under a single semver-tracked binary version (`rustc 1.86.0` in early 2026), but the *language itself* is partitioned into named **editions** — Rust 2015, Rust 2018, Rust 2021, **Rust 2024** (stabilised 2025-02-20 with Rust 1.85, the migration tool generally available in 1.86+). Each source file declares its edition in `Cargo.toml` via `edition = "2024"`; the compiler reads the declaration and applies the edition's syntax and semantic rules to that file. **Different editions can be linked together in the same binary** — a v2018 crate calls a v2024 crate calls a v2021 crate, all in one `cargo build`. This is the breakthrough that semver alone cannot deliver: breaking changes are *opt-in per source file*, not forced on the world by a major version bump. The Rust 2024 edition (the most recent at time of writing) introduced changes to closure capture rules, lifetime elision in async blocks, and the `unsafe` requirement on certain attributes — none of which broke any pre-2024 Rust code, because pre-2024 code declares its older edition and the compiler applies the older rules to it. The cost is implementation complexity (the compiler is essentially several languages in one binary) and conceptual load on the user (which edition rules apply to *this* file?). **Pick edition-based versioning when {{project.name}} is a general-purpose language with multi-year language-design horizons, when the implementation can absorb the per-edition rule-application cost (typically via a `parse-with-edition` mode in `TOOLCHAIN.md §1` parser), and when the team is committed to the discipline of designing editions as coherent thematic releases rather than dumping grounds.** Editions are most defensible at v1.0+ once the core language has stabilised; before v1.0, semver alone is fine.
- **Hybrid: semver + editions.** Rust is technically this — Rust the compiler is semver-versioned (`rustc 1.85`, `rustc 1.86`); Rust the language is edition-versioned (Rust 2024 was *introduced* in Rust 1.85, stabilised in 1.86+). The semver number tracks *implementation* breakages (`unsafe` API changes in the compiler's library, performance regressions, ABI flips); the edition tracks *language* changes. Most new languages will end up here implicitly the moment they introduce their second edition. **Pick the hybrid when you want both — and you will, eventually.**
- **Continuous (no versions, the Bazel rules / Go internal model).** A single ever-advancing trunk; users pin by commit SHA, not by version number. Acceptable for internal-to-a-company languages and for build systems where the commit-pinning workflow is already standard. Generally inappropriate for a public-facing language because the package manager ecosystem assumes versions. **Avoid for {{project.name}} unless it is explicitly internal-only.**
- **CalVer (date-based versioning, YYYY.MM.PATCH).** Used by Ubuntu, Unity, JetBrains, and a long tail of products where "what shipped in 2024 March" is the operative question users ask. Semver and CalVer can coexist (Python uses semver-flavoured versioning for its releases but the *release cadence* is annual-major / quarterly-bugfix, which is calver-like in practice). **CalVer is uncommon for programming languages** — users expect semver because their build tooling does — but a language with an explicit annual release cadence (Go's six-month cadence, Java's six-month cadence) can use CalVer informally without changing the semver-typed wire format. Not recommended as a *primary* versioning scheme for {{project.name}}.

**State the choice and the operational consequence.** If semver, write the v1.0 commitment criteria — what set of features must be stable before v1.0 ships, after which MAJOR-bumps become rare? If edition-based, write the v0.1 edition name (probably the year), the cadence for new editions (Rust's is roughly three years — 2015, 2018, 2021, 2024), and the *editor-of-record* per edition (who curates the changes). Cross-link `BOOTSTRAP_PLAN.md §3` — the self-hosting phase milestones are *expressed in versions defined here*; "Phase 2 bootstrap proof: v1.5" only means something once §1 has committed to what v1.5 *is*.

## 2. Stability tiers

Within a release, which features are stable (use in production), which are beta (we mean it but reserve the right to break), and which are experimental playgrounds (use at your own risk)?

- **Three-tier system: stable / beta / nightly (the Rust release-channels model).** The compiler ships in three concurrent channels — `stable` (the current released version, frozen-feature-set), `beta` (the next stable release, in the six-week stabilisation window), and `nightly` (the bleeding edge, rebuilt every night from `master`). Each channel produces a separate binary with its own version number. **Unstable features are gated behind opt-in attributes** — Rust's `#![feature(generic_const_exprs)]` (an unstable feature flag at top-of-crate level) is the canonical reference; the compiler refuses to compile code using `#![feature(...)]` on the stable channel, requiring users who want experimental features to *consciously opt in* by switching to nightly. This is the strongest possible commitment to stability: stable users **literally cannot accidentally use an unstable feature**, because the compiler enforces the gate. The cost is operational — running three release channels is three CI matrices, three artefact pipelines, three docs sites. **Pick the three-tier system when {{project.name}} expects production users at scale and is willing to pay the channel-multiplication cost.** This is the right answer for any general-purpose language with v1.0+ ambitions.
- **Two-tier system: stable / experimental (the Go model).** A single release channel for general use; experimental features ship behind explicit `GOEXPERIMENT=` environment variables or `//go:build experimental` build tags. No separate nightly channel — the master branch is the next release, with experimental code gated. Simpler to operate (one release channel, one artefact pipeline) at the cost of less granular user control. **Acceptable for {{project.name}} v0.1 through v1.0; revisit once the language has multiple competing experimental features that need independent stabilisation timelines.**
- **Single-tier (everything is stable, the Elm model).** Elm's commitment: there is no experimental tier — features ship when they ship, and they are stable on day one. The cost is glacial pace (Elm 0.19 released 2018, 0.19.1 released 2019, and as of 2026 there has been no Elm 0.20); the benefit is unmatched user trust ("everything you see in the docs works and will keep working"). **Pick single-tier when {{project.name}} is small-language by intent — a DSL, an educational language, a deliberately limited scope — and the team values stability over feature velocity.** Inappropriate for ambitious general-purpose languages.
- **Feature-flag system regardless of tier count.** Whatever number of tiers, *individual experimental features are independently gated*. Rust's `#![feature(let_chains)]`, `#![feature(generic_const_exprs)]`, `#![feature(try_blocks)]` are each independent flags; a nightly user opts in to specifically the experimental features they want, not "all experimental features at once". This is the right granularity for any language with more than two experimental features in flight at once. The implementation cost is per-feature gate-checking in the parser / type-checker / codegen; the design cost is naming and documenting each flag. **Adopt feature-flag gating from v0.1** even if you have only one experimental feature today — adding the mechanism later is more expensive than starting with it.
- **Per-edition feature gating.** When using edition-based versioning (§1), experimental features can be gated to opt-in *only when the file declares the latest edition*. This combines the safety of feature flags with the per-file granularity of editions. Rust 2024 introduced this pattern formally: certain features become stable only on the 2024 edition, leaving the 2021-and-prior editions on the older feature set forever. **Use this in combination with §1 edition-based versioning** to make stabilisation thematic — "the 2024 edition stabilises X, Y, Z" reads as a coherent narrative, not a random feature list.

**State the tier model, the feature-flag mechanism, and the promotion criteria** — what does a feature have to demonstrate before it graduates from nightly to stable? Rust's process: an RFC accepting the feature (§4), an implementation behind `#![feature(...)]`, at least one full release cycle (six weeks) of nightly soak time, a stabilisation report documenting issues found and resolved, and a final stabilisation PR. Adopt or adapt; do not skip the criteria — features that ship to stable without a soak period are features that ship known bugs to production.

## 3. Breaking change policy

What is allowed to break between releases, and what is forbidden?

- **Semver-major-only (the strict-semver model).** Breaking changes are concentrated in MAJOR-version bumps; MINOR and PATCH releases preserve every previously-working program. The Cargo / npm / pip / Go modules ecosystems all *enforce* this assumption at the package-resolution layer; deviating from it causes user pain disproportionate to the engineering convenience. **The minimum-acceptable commitment for any language with a package ecosystem.** The cost is that MAJOR bumps become rare and high-stakes (Python's 3.0 release lessons): once you commit to "we break in MAJOR releases only", you implicitly commit to "MAJOR releases are once a decade" because the user cost of forcing a migration is enormous. **Pick this when {{project.name}} ships without an edition system and expects to live on its v1.x line for many years.**
- **Deprecation cycle (warn-then-break, the Java model).** Breaking changes are preceded by a deprecation cycle: the about-to-break behaviour is marked deprecated for N releases, the compiler emits warnings, users have a documented runway to migrate, and only after N releases does the deprecated behaviour become an error. Java's deprecation cycle is the multi-decade reference; Python's `DeprecationWarning` is the lighter-weight version. The cost is the long tail — Java has deprecated APIs that are still callable two decades later because nobody has the political will to remove them, leaving the language carrying ancient cruft forever. **Combine deprecation with editions or major-version bumps** so that the deprecation has a *terminal date*, not an indefinite warning.
- **Never (the Go 1.x compatibility promise).** Go's "compatibility 1" promise (2012, ongoing) is the strongest stability commitment in any modern mainstream language: programs that compile under Go 1.0 still compile under Go 1.22 (the latest at time of writing) without modification. The cost is enormous design pressure on every Go 1.x release to avoid breakage even at the cost of suboptimal feature design — generics took eight years (2012-2020) partly because the design had to slot into the compatibility-1 promise. The benefit is the most production-stable language in widespread use. **Pick "never" only when {{project.name}} is willing to absorb the design constraint indefinitely — typically when the language is sponsored by an organisation that values its own internal codebase's longevity above all else (Google's Go, Microsoft's C#'s longer-than-most stability promises).**
- **Edition migration tool (the Rust 2018/2021/2024 model).** Breaking changes ship in editions (§1); migration to the new edition is *automated by tooling*. **`cargo fix --edition`** (Rust's flagship migration command) reads the user's existing crate, applies the syntactic and semantic changes the new edition requires, and emits a patched crate that compiles under the new edition. The user reviews the diff and commits; no manual rewriting required for the mechanical changes. The Rust 2024 migration (stabilised 2025-02) used this tool extensively — large codebases that would have been weeks of manual work were minutes of `cargo fix --edition` plus code-review. The cost is engineering investment in the migration tool itself (an extra subsystem of the compiler that knows how to *rewrite* programs, not just *check* them); the benefit is that breaking changes become technically survivable at scale. **Pick the edition-migration-tool model when §1 commits to edition-based versioning and {{project.name}} expects to ship breaking edition changes regularly.** This is the 2026 gold-standard answer for a general-purpose language.
- **Hybrid: deprecation cycle + edition migration.** Combine: deprecate in the current edition (warnings), break in the next edition (errors), provide migration tool to cross the boundary. This is the model Rust uses in practice — the 2024 edition's changes were warned-about throughout the 2021 edition's lifetime, then enforced as the file opts into 2024, with `cargo fix --edition` handling the mechanical migration. **The recommended default for a v1.0+ general-purpose language with editions.**

**State the policy and the operational guarantees.** Example commitment: "Within an edition, no breaking changes. Across editions, mechanical breaking changes only — anything `cargo fix --edition` can handle automatically. Semantic breaking changes (changing the meaning of valid code without changing its syntax) are forbidden in any release." Cross-link §6 (the tooling that makes this safe) and §4 (the RFC process that gates which changes are allowed to be breaking).

## 4. RFC process

How does a feature idea become an accepted feature, and how does the project document why some ideas are rejected?

- **Informal proposals (the early-language model).** Issues on GitHub / GitLab / the issue tracker; maintainer reads, discusses in comments, decides. Acceptable when the project has fewer than ~50 contributors and changes are mostly incremental. Becomes inadequate once the project has external stakeholders who need a *legible* process to understand how decisions are made.
- **Formal RFC repository (the Rust RFCs model).** A dedicated git repository (the **Rust RFCs repo** — `rust-lang/rfcs` on GitHub, ~3600 PRs as of early 2026, ~1500 merged RFCs since 2014) where each substantial language change is proposed as a Markdown document in a pull request. The PR template includes mandatory sections: **Summary** (one paragraph), **Motivation** (why does this problem exist?), **Guide-level explanation** (how a user would learn this feature), **Reference-level explanation** (how this feature actually works in the compiler), **Drawbacks** (why we might not want this), **Rationale and alternatives** (what else did we consider?), **Prior art** (how do other languages do it?), **Unresolved questions** (open issues to address), **Future possibilities** (what does this unlock?). The PR sits open for at least a 10-day **Final Comment Period (FCP)** before merge, allowing community input. The decision is made by the relevant language team via consensus or vote (see §5). Merged RFCs are *accepted*; closed-without-merge RFCs are *rejected* (and the close-comment documents why); withdrawn RFCs are *withdrawn* by the author (no longer pursued). Every merged RFC gets a tracking issue in the implementation repository (`rust-lang/rust`) that tracks implementation progress through `#![feature(...)]` gating to stabilisation. **Adopt the Rust RFCs model directly for any language with v1.0+ ambitions.** It is the most-studied, most-copied process in the open-source PL world; reinvention is wasted effort.
- **Accepted / rejected / withdrawn states.** Whatever the process, every RFC ends in one of three terminal states: **accepted** (merged into the RFCs repo, tracked for implementation), **rejected** (closed with a written explanation; the RFCs repo's `closed` view is the archaeological record of "what did we consider and decline?"), or **withdrawn** (the author closes the PR, typically because they changed their mind or addressed the problem differently). The rejection-with-rationale is the most valuable artefact — future RFC authors search the closed PRs for prior art on their idea, and the rejection comment teaches them what arguments did not work last time. **Maintain rejection rationale as a public corpus**, not as private maintainer memory.
- **The lightweight-RFC variant (the Python PEPs model).** Python Enhancement Proposals (PEP 1 onward, ~700 PEPs as of 2026) are similar to Rust RFCs in spirit but live in a separate `peps` repository and use a longer-form structured document. PEPs are slower (typical PEP timeline is months to years from draft to acceptance) and more aspirational than Rust RFCs; many PEPs document policy or non-language conventions rather than language changes. **Use PEPs as a reference for documenting non-language decisions** (release cadence, governance, deprecation policy) even if §4 of {{project.name}} uses Rust-style RFCs for language changes.
- **In-tree RFC documents.** Some projects (Swift Evolution, Elixir, Erlang) keep RFCs in the main repository rather than a separate one. This is simpler operationally — one repo, one PR workflow, one issue tracker — but loses the separation between *proposing* and *implementing* a change. Acceptable for smaller projects; the cost-of-coupling grows with the project size. **Default to a separate RFCs repo at v1.0+ scale.**

**State the RFC repository location** (`{{project.name}}-lang/rfcs` on GitHub is the conventional naming), the template path (`0000-template.md` is the Rust convention), the required sections (copy from the Rust RFCs template; adapt to the language), the Final Comment Period length (10 days is the Rust default; shorter is fine for smaller projects), and the merge authority (cross-link §5). Provide a v0.1 starter RFC repository with at least the template document, the README, and a "how to write an RFC" guide so the process is *usable on day one* rather than promised-for-later.

## 5. Decision-making model

When the RFC process produces disagreement, who has the authority to decide?

- **BDFL — Benevolent Dictator For Life (the early-Python / early-Ruby model).** A single individual — Guido van Rossum for Python until 2018, Yukihiro "Matz" Matsumoto for Ruby — holds final authority over language design decisions. Decisions are fast (no committee dynamics, no quorum-waiting), coherent (one taste, one vision, one veto), and personal-trust-based (the community trusts the dictator's judgement, or they fork). The cost is succession — Python's 2018 transition out of BDFL governance (Guido stepped down after the PEP 572 walrus-operator dispute exhausted him) was the test case for "what happens when the BDFL leaves?". Python's Steering Council model emerged from that transition and is the modern-Python governance structure. **Pick BDFL only when {{project.name}} has a founder with the capacity, willingness, and lifelong commitment to play the role**, and write a documented succession plan (cross-link `CONTRIBUTING.md` and the project's governance document). Otherwise, plan for committee governance from day one.
- **Steering committee / language team (the Rust / Python-post-2018 / TC39 model).** A small group — typically 3 to 9 people — holds collective authority. Rust's structure: per-domain teams (Language Team, Library Team, Compiler Team, etc.), each ~4-8 members elected by team consensus, with cross-team coordination via the Leadership Council. Decisions are made by team consensus (formal vote rare; "disposition: merge" with no member objection is the typical merge path on RFCs). The cost is committee dynamics (longer decision cycles, the need to keep members aligned on long-running threads); the benefit is robustness (no single point of failure), legitimacy (decisions are *seen* to be made by a representative body), and the implicit professional norm that team members earn their seat by track record. **The 2026 default model for any language with v1.0+ ambitions and an active contributor community.**
- **Consensus of maintainers (the early-Linux / many-small-projects model).** Authority diffuses across "everyone with commit access" — a maintainer accepts a change if no other maintainer objects, with vague-by-design conflict-resolution. Works for small projects; scales poorly past ~10 active maintainers because the implicit "no objection" rule degrades into "nobody noticed". Not recommended as a *primary* model for {{project.name}}; consensus is good for routine work but needs a fallback authority (BDFL or committee) for genuine disputes.
- **Foundation governance (the Eclipse / Linux Foundation / Rust Foundation 2021+ model).** A legal foundation owns the trademark and project assets, with a Board of Directors (often drawn from corporate sponsors) and a separate technical-decision-making body (the language teams). The foundation handles *non-technical* questions — trademark licensing, fundraising, contributor agreements, code-of-conduct enforcement — leaving technical authority with the language teams. **Adopt foundation governance at the v2.0+ scale when {{project.name}} has corporate users, a budget that needs managing, and a trademark worth defending.** Premature for v0.1-v1.0.

**State the model, the team or individual who currently holds authority, and the succession or election mechanism.** Cross-link `CONTRIBUTING.md` for the practical-contributor-experience side (how do I, as a non-maintainer, become a maintainer?) and the project's `GOVERNANCE.md` (often a separate document at the repository root) for the formal governance text. For v0.1 projects, a one-paragraph commitment ("Decisions are made by the {{project.name}} maintainers via consensus; tie-breaks by the founder {{founder.name}}") is sufficient — formal governance documents come at v1.0+.

## 6. Backwards-compatibility tooling

What tools carry users' existing code across the breaking changes that §3 permits?

- **The `--edition` flag (the Rust model).** The compiler reads each source file's edition declaration and applies edition-specific rules. The same compiler binary handles all editions; users can mix editions across crates within a single build. This is the *enabling primitive* for everything else in this section — without per-file edition awareness, edition-based versioning (§1) and the migration tool (below) are not possible. **Implement edition-aware parsing and type-checking from v0.1** if §1 commits to editions, even if v0.1 has only one edition; retrofitting edition-awareness into a compiler that was built assuming one language is multi-engineer-month work.
- **The migration tool — `cargo fix --edition` (the canonical reference).** A compiler subsystem that *rewrites* user code to the new edition, applying the mechanical syntactic changes the new edition requires. Implementation: the migration tool runs the parser, walks the AST, identifies edition-specific patterns (e.g., "in Rust 2018, `dyn Trait` was optional; in Rust 2021, it is required"), and emits a rewritten source file with the changes applied. The tool emits a diff for the user to review and commit; no auto-commit. Limitations: the tool handles *mechanical* changes (syntactic transformations with a deterministic rewrite); it cannot handle semantic changes that require user judgement (e.g., "this code's behaviour changed; you must decide which new behaviour you want"). **Build the migration tool as part of the compiler binary, not as a separate project** — the migration tool and the compiler must share the same parser, type-checker, and edition-awareness logic, or they will drift. The 2025 Rust 2024 migration was the largest validation of this approach to date.
- **A linter that warns about deprecations (`clippy` and `rustc`'s `#[deprecated]` attribute as references).** Before a feature is removed, it is marked deprecated; the linter emits a warning at every use site; the user has the lifetime of the deprecation cycle to migrate. Combine with the migration tool: deprecation warnings tell the user *what* to migrate; the migration tool *does* the mechanical migration. **Adopt deprecation warnings from v0.1**, even if the actual breaking changes are years away — the muscle memory of "warn first, break later" is the cheapest social capital in language evolution.
- **Upgrade scripts (the language-package-manager interface).** Some languages have explicit upgrade scripts that handle multi-version migration — `pyupgrade`, `2to3`, `rustfix`, `gofmt -r`. These are typically less ambitious than a full edition migration tool but cover smaller-scope refactorings ("rename this method", "change this import path"). **Ship language-specific upgrade scripts via the standard package manager** (`{{project.name}} fmt --rewrite=...`, `{{project.name}} fix --rewrite=...`), not as separate side-projects, to keep them discoverable.
- **A documentation generator that surfaces deprecation timelines.** The docs (`TOOLCHAIN.md §5`) should show, for every deprecated feature, the version in which it was deprecated, the version in which removal is planned, and the recommended replacement. Users planning a migration consult the docs first, run the migration tool second, code-review third, commit. **Wire deprecation metadata into the docs generator from v0.1**; retrofitting it later means manually annotating every previously-deprecated feature.
- **CI for the migration tool itself.** The migration tool is *tested by running it on a corpus of real-world {{project.name}} code* and verifying that the output compiles under the new edition and produces semantically-equivalent behaviour. Rust's `crater` (the regression-testing tool that runs `cargo build` against the entire crates.io ecosystem) is the canonical reference for "test your migration tool against the world before you ship it". For pre-ecosystem languages, the test corpus from `BOOTSTRAP_PLAN.md §4` plus `TESTING_STRATEGY.md` is the equivalent: test the migration tool against your own test suite plus any external real-world programs you can find.

**State which tools ship in v0.1 versus later versions.** Realistic v0.1 commitment: `--edition` flag (if §1 chose editions), `#[deprecated]` attribute and lint, basic docs-generator integration. v0.5+ commitment: the migration tool itself. v1.0 commitment: full edition migration validated against the in-tree corpus. v2.0+ commitment: crater-style regression testing against the real-world ecosystem.
