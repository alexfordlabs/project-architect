# Toolchain — {{project.name}}

This document captures the **developer-facing tooling** that ships alongside {{project.name}} — the REPL the user types into, the formatter they run on save, the linter that flags their mistakes before CI does, the LSP server that powers their editor's autocomplete, the debugger that lets them step through a failing test, the package manager that fetches their dependencies, the build tool that turns sources into artefacts, the documentation generator that publishes their API reference, and the test runner that gives them green checks. Together these are the *experience* of using {{project.name}} on Tuesday afternoon — not the language proper, but the part of the language a working programmer touches every fifteen minutes.

`LANGUAGE_GRAMMAR.md` pinned the syntax the user types; `SEMANTICS.md` pinned what their programs mean; this document pins the *workflow* that surrounds writing those programs. A language with beautiful semantics and a broken formatter ships fewer programs than a language with mediocre semantics and `gofmt`. The Go team has been explicit about this for over a decade — Rob Pike's 2012 talk *"Go at Google"* makes the point that `gofmt`-on-save eliminated whole categories of code-review noise from the language's first year onward. The 2026 lesson is the same one Go taught in 2009: **shipping the toolchain together with the language, designed-as-a-set, is a force multiplier that no after-market third-party tooling can match.**

Ten axes are surfaced because each one is an independent product decision with a long compounding effect on adoption. Skipping a REPL costs you two years of pedagogical material (every introductory tutorial reaches for `>>>` first). Choosing an opinionated formatter (`gofmt`, `rustfmt`, `biome`) versus a configurable one (early `prettier`, `black --line-length=…`) commits you to a different community culture — opinionated formatters end style debates by fiat, configurable ones perpetuate them as `.editorconfig` discoveries forever. Targeting **LSP 3.17** versus rolling a custom protocol is the difference between "works in VS Code, Neovim, Helix, Zed, Emacs, IntelliJ on day one" and "users wait three years for a community Neovim plugin". Decide each axis deliberately, name a 2026 production exemplar, and write the rationale into the implementation plan — the developer-experience surface, like the standard library, is forever-compatibility territory once published.

## 1. REPL

Does {{project.name}} ship an interactive read-eval-print loop?

- **Line-at-a-time REPL.** One expression per line, immediate result. The minimum viable REPL — Python's `python` prompt, Ruby's `irb`, Node's `node` prompt, GHCi's `:` commands. Easy to implement (call the parser on each line, evaluate, print), works adequately for exploration, breaks down the moment the user wants to define a multi-line function or paste a 40-line snippet. Suitable for query languages, configuration languages, and DSLs where the unit of input *is* a line.
- **Multi-line REPL with continuation detection.** The REPL recognises an incomplete expression (open paren, unfinished function definition, unterminated string) and prompts for continuation with a secondary prompt (`...` in Python, `*` in some Lisps, `|` in Elixir). Almost every modern REPL belongs in this category — Python 3.13's PyREPL (Oct 2024 rewrite by Pablo Galindo and Lysandros Nikolaou, based on the PyPy REPL with syntax highlighting and multiline editing), Rust's `evcxr`, OCaml's `utop`, Elixir's `iex`. The 2026 baseline.
- **Notebook-style cells / IPython-class REPL.** Each "cell" is a self-contained block; cells can be re-executed in any order; state persists across cells; rich output (HTML, images, tables) is rendered inline. IPython (the foundation of Jupyter), Pluto.jl (Julia — reactive cells where re-evaluating one cell automatically re-runs its dependents), Observable for JavaScript. Heavy investment, but pays for itself for data-science / scientific-computing audiences — if {{project.name}} targets numerics or ML workloads, this is table stakes; if it targets systems programming, line-at-a-time is sufficient.
- **No REPL.** Some languages deliberately ship no REPL — Go does not (`go run` plus `fmt.Println` substitutes), Rust shipped `evcxr` only as a community project (still not in the official toolchain), C and C++ have only fragile experimental REPLs (`cling`, `cppinsights`). For compiled languages with heavy type inference or compile-time machinery, a real REPL is genuinely hard — you would need an incremental compiler. Acceptable for systems languages; harmful for teaching languages.

**State the choice and the interaction model.** If you ship a REPL, commit to: line editing (Readline / `rustyline` / `reedline`), history persistence (`~/.{{project.name}}_history`), tab completion (calls into the LSP server? a stripped-down completer? none?), syntax highlighting in-prompt (Python 3.13 ships this; older Python did not). For `paradigm == "functional"`, expect the REPL to be load-bearing — Haskell, OCaml, and Scheme communities live in their REPLs and treat the file-editor workflow as a secondary mode.

## 2. Formatter

Does {{project.name}} ship a canonical code formatter, and is it opinionated or configurable?

- **Opinionated, zero-config (`gofmt` school).** One canonical style, no flags, no `.formatter.config`. `gofmt` (Go, 2009 — the prototype), `rustfmt` (Rust — slightly less rigid than `gofmt`, accepts a small `rustfmt.toml` but the community treats defaults as the only acceptable style), `zig fmt` (Zig), `dart format` (Dart — Google's flagship Dart-format-on-save culture is the 2026 reference), Elm. The trade is: you lose the ability to express stylistic preference; you gain (a) zero style-debate overhead in code review, (b) automatic format-on-save in every editor with one binary, (c) the ability to autoformat in pre-commit hooks without conflict. **The 2026 default for new languages is opinionated** — every successful language since 2009 (Go, Rust, Elixir's `mix format`, Zig, Dart, Roc) has shipped opinionated formatting and the ergonomics gap to "configurable" languages is now visible to users.
- **Configurable (`prettier`/`black` school).** A formatter with knobs: line length, quote style, trailing commas, indent width. **Biome v2.4** (February 2026 release — adopted at AWS, Google, Microsoft, Cloudflare, and Vercel; the spiritual successor to Prettier with 10-20× faster performance because it is written in Rust and shares a CST with its linter) is the 2026 reference for the JS/TS world. `black` for Python (originally pitched as opinionated — "the uncompromising code formatter" — but has accrued `--line-length`, `--skip-string-normalization`, `--target-version` over time). The trade-off is the inverse: you gain per-team customisation; you pay in style debates and in editor-config sprawl. **Acceptable when the language already lives in a wider ecosystem (JS/TS, Python) where users expect to customise — costly when starting from scratch.**
- **Not provided.** C, C++, and pre-2010 languages ship no canonical formatter. The market response was `clang-format` (a community-driven, configurable, opinionated-defaults tool — now de facto for C/C++), and the cost of *not* shipping one is decades of style-war scar tissue in every C/C++ codebase. **In 2026, "no formatter" is malpractice for a new language.**

**State the choice and the integration story.** Format-on-save in editors (the LSP server typically exposes `textDocument/formatting` and `textDocument/rangeFormatting` — see §4). Pre-commit hook support (`prek` — modern Rust-based reimplementation of `pre-commit`, faster, increasingly the 2026 default). CI check (`{{project.name}} fmt --check`). For configurable formatters, the config file format (TOML is the 2026 default — see Rust, Cargo, Biome v2's TOML config option) and the discovery rule (search upward from the file? a global default?). Cross-link to `LANGUAGE_GRAMMAR.md` — the formatter consumes the same CST the compiler does, so it must agree on tokenisation (especially trailing-comma handling in lists, semicolon-insertion if you have ASI, and whitespace-significance for indent-based grammars).

## 3. Linter

How does {{project.name}} surface stylistic and correctness warnings beyond the type checker's hard errors?

- **Separate tool.** A standalone linter binary the user runs after the compiler. `eslint` (JS — separate from `tsc`), `clippy` (Rust — separate from `rustc`, ships *with* the toolchain via `rustup component add clippy`), `golangci-lint` (Go — community aggregator over `vet`, `staticcheck`, and a long tail of analysis passes), `ruff` (Python — Rust-written, ~100× faster than `flake8`+`pylint`, 2026 dominant), `Biome v2.4`'s linter half. Separation lets the linter iterate faster than the compiler (lints can become smarter without bumping the language version), and lets advanced users opt out cheaply.
- **Integrated with the type checker.** Lints are emitted by the same compiler pass that emits type errors, distinguished only by severity. **Roc** does this — its compiler emits warnings inline with errors using the same engine. **Elm** is famous for the "Elm-style error message" approach, where every diagnostic — error or lint — gets the same humane treatment. Integration buys you (a) one diagnostic stream for the editor / LSP to consume, (b) lints that can use the full type information the compiler has computed, (c) zero discovery problem (the user is already running the compiler). Pays in compiler complexity and in deprecation friction (removing a lint = changing the compiler).
- **Not provided.** Skip only for very small languages (configuration languages, query DSLs) where there is no useful lint surface. For everything else, "no linter" forces the community to invent one in five years and you live with the resulting fragmentation forever (cf. Python's `pyflakes` vs `pylint` vs `flake8` vs `pylama` vs `prospector` vs `ruff` arc from 2001 to 2024).

**The 2026 production exemplar is `clippy`** — over 700 individual lints organised by category (`correctness`, `style`, `complexity`, `performance`, `pedantic`, `nursery`, `restriction`), with each lint having a stable name, a "why is this bad?" explanation, a "good vs bad" code example, and a per-project allow/warn/deny configuration. If you ship a linter, ship it with that level of UX investment from day one — half-finished linters get turned off by frustrated users and never re-enabled.

## 4. LSP / IDE integration

How do editors talk to {{project.name}}'s analysis engine?

- **Language Server Protocol (LSP) is the universal answer in 2026.** Microsoft published LSP 1.0 in 2016, and every editor that matters now speaks it natively: VS Code, Neovim, Vim (via `coc.nvim` / `nvim-lspconfig`), Helix, Zed (built-in, no plugin), Emacs (built-in `eglot` since Emacs 29, plus `lsp-mode`), IntelliJ family, Sublime Text. Roll your own protocol and you lose all of them. **Target LSP 3.17** — the current stable version, finalised in 2022, with comprehensive support for semantic tokens, inlay hints (the dotted "you have a variable named `x` of type `i32` here" annotations every modern editor renders), call hierarchy, type hierarchy, code lenses, notebook documents. **LSP 3.18 is in development** as a working draft with new features around proposed-feature stabilisation — treat it as a watch-item, not a target; do not ship pre-3.18 features your users cannot consume.
- **Incremental parsing — tree-sitter v0.26.x.** The 2026 default for editor-side syntax highlighting and structural navigation is **tree-sitter** (Max Brunsfeld et al., now at v0.26.x as of late 2025 / early 2026). It is the default parser in Zed, Neovim (`nvim-treesitter`), Helix, and Emacs 29+ (built-in `treesit.el`). Tree-sitter gives you (a) incremental re-parse in O(diff-size) on each keystroke, (b) syntactically-aware selection (`expand-region`-class commands), (c) highlight-injection (so `<script>` content inside HTML gets JS highlighting), (d) structural editing. **Ship a `tree-sitter-{{project.name}}` grammar alongside your language at v1.0 release** — every editor will pick it up automatically, you save a tier of tooling work, and you align with the dominant 2026 ecosystem. Cross-link `LANGUAGE_GRAMMAR.md` — your tree-sitter grammar must agree with your real parser on token boundaries.
- **Reference architecture: `rust-analyzer`.** The 2026 canonical "how to build a language server" reference is `rust-analyzer` (now bundled with `rustup` as `rust-analyzer` since Rust 1.65, 2022). Its architecture: **Salsa** for incremental computation (cached, query-based, automatically invalidated on dependency change), **rowan** for lossless syntax trees (a Rust port of the IntelliJ PSI design — preserves comments, whitespace, and original byte spans, essential for a formatter and a refactoring engine), and a thin LSP adapter on top. Read the `rust-analyzer` book if you are building a new language server — the design generalises and you will reinvent it badly if you do not.
- **Custom protocol.** Effectively never the right answer in 2026. The only exception is languages with editor-specific extension points so deep that LSP cannot express them (full IDE-grade refactoring frameworks like IntelliJ's PSI). Even there, the standard play is "speak LSP for the universal subset, expose a private extension protocol for the rest" — see how Kotlin and Scala both ship LSP servers plus IntelliJ-native plugins.

**State the choice and the implementation budget.** A serious language server is *the* longest-lived piece of tooling you will build — `rust-analyzer` has had ~200 active contributors over six years and over 8,000 merged PRs. Scope accordingly: a minimal LSP (hover, go-to-definition, diagnostics, formatting) is 4-6 engineer-months; a polished one (rename, refactor, code actions, semantic tokens, inlay hints, call hierarchy, workspace symbols) is multi-year.

## 5. Debugger

Can the user step through a {{project.name}} program?

- **Interpreter introspection.** For interpreted languages with a tree-walker or bytecode VM, the cheapest debugger is one that pauses the interpreter loop at named breakpoint sites and exposes the local environment. Python's `pdb` (since 1.4, 1996), Ruby's `byebug` / `irb` integration. Limited to the language's own runtime; works only when you control the evaluator. Suitable for tree-walking interpreters and bytecode VMs; not applicable to native-code outputs.
- **Debug Adapter Protocol (DAP).** Microsoft's editor-protocol counterpart to LSP — DAP standardises the messages between editors and debuggers (set breakpoint, continue, step over, evaluate-in-frame). Every editor that ships an LSP client now also ships a DAP client: VS Code, Neovim (`nvim-dap`), Helix, Emacs (`dape`). **DAP is capability-flag-versioned** — the protocol evolves by adding new capabilities advertised in the `Initialize` response, so an editor and adapter from different years still interoperate at the intersection of their capabilities. **CLion shipped DAP support in February 2026**, and **CLion 2026.1** adds DAP-over-TCP for remote debugging (previously stdio-only); these are signals that the protocol is now table stakes in the JetBrains world too. **Ship a DAP adapter, not a custom protocol.** The 2026 ecosystem is uniform.
- **Native debugger integration.** If your language compiles to native code (LLVM, Cranelift, custom backend), the debugger story is "emit DWARF 5 debug info, let `gdb` / `lldb` do the rest, ship a small wrapper that maps DWARF back to {{project.name}}'s source names for pretty-printing". Rust does exactly this — `rust-lldb` / `rust-gdb` are thin wrappers that load Rust-aware Python formatters into `lldb` / `gdb`. Pays a learning curve on DWARF emission; reuses thirty years of `gdb`/`lldb` UI investment for free.
- **Time-travel debugging.** Step backwards. **rr** (`rr-project.org`) for Linux native code is the production reference; replay-debuggers are powerful but operationally heavy (record everything, reproduce deterministically). Aspirational for a v1; reasonable for languages with substantial enterprise / systems-programming uptake.
- **No debugger.** Acceptable only for very small DSLs and query languages where the unit of debugging is "look at the result". For anything Turing-complete, "no debugger" leaves your users in `print`-debug-land forever; that is a known cost.

**State the choice and the protocol.** Decide on DAP capability set: launch, attach, breakpoints (line, function, conditional, hit-count), stepping (over, into, out), variable inspection, watch expressions, `evaluate` for REPL-in-debugger, exception breakpoints. Cross-link `SEMANTICS.md` — what counts as a "stack frame" is a semantics decision (does tail-call elimination collapse frames? do `async` resumptions appear as separate frames?).

## 6. Package manager + registry

How do users add a third-party library to a {{project.name}} project?

- **Bundled, language-team-owned.** Ships in the toolchain, designed alongside the language, integrated with the build tool and the test runner. **`cargo` (Rust)** is the 2026 reference — one tool covers `init`, `add`, `build`, `test`, `bench`, `run`, `doc`, `publish`, `install`, and `audit`, with `crates.io` as the canonical registry. **`go mod`** (Go 1.11+, 2018) is the alternative reference, philosophically simpler: no central registry, packages are imported by Git URL (`github.com/foo/bar`), minimum-version selection (MVS) for resolution. Bundled package managers are the 2026 default for new languages — leaving package management as a "user problem" creates a fragmentation cost (Python: `pip` + `setuptools` + `poetry` + `pdm` + `hatch` + `rye` + `uv`, each with a partial overlap).
- **External community standard.** No first-party tool; the community converges on one (`npm` for Node, eventually displaced by `pnpm` and `bun`; `pip` for Python, displaced by `uv` from Astral as the 2026 dominant choice — Rust-written, 10-100× faster than `pip`). Costly to bootstrap (every new language goes through "which package manager?" wars for years); allows the community to iterate on package management without bumping the compiler.
- **Not provided.** Acceptable for embedded / niche languages where users vendor dependencies manually. Costly for everything else.

**Version resolution algorithm:**

- **Semver-with-SAT-solver.** `cargo`, `npm` (since v7), Bundler. Each dependency declares a semver range; the resolver finds a set of versions satisfying all ranges. NP-hard in the general case, well-engineered in practice. Surface "no compatible versions" errors clearly — the worst UX failure mode is a 2,000-line "conflict" report nobody can parse.
- **Minimum-version selection (MVS, Go-style).** Each dependency declares an *exact* minimum; the resolver picks the *minimum* version that satisfies all minimums. Deterministic, no SAT solver, no "lock file drift" (the lock file is the union of declared minimums). The trade-off is that MVS lags behind the latest releases — users must opt in to updates explicitly. Russ Cox's 2018 article *"Minimum Version Selection"* makes the case; in 2026 the lesson is "MVS is excellent if you can convince your community to use it; semver-range resolution is what most ecosystems will demand."
- **Lock-file-based.** `Cargo.lock`, `package-lock.json`, `poetry.lock`, `go.sum`, `uv.lock` — capture the exact resolved versions for reproducible builds. **Commit lock files for binaries, exclude them for libraries** is the 2026 consensus, with Cargo's `--locked` flag as the CI-side enforcement mechanism.

**Registry design:**

- **Centralised registry** (`crates.io`, `npm`, `pypi`): one canonical place, all packages, search-friendly, the trust target. Pays in security investment (typosquatting, malicious publishes, supply-chain auditing) and in operational overhead (downloads, mirroring, CDN).
- **Decentralised** (Go modules via Git URLs): no central registry, packages are wherever they live. Cheap to bootstrap; pays in search/discovery problems and in "what if GitHub goes down?" availability.
- **Hybrid** (Deno's URL imports + JSR registry from 2024): direct URL imports as the protocol, an optional registry layer on top. Newer experiment; worth watching for v2 language design.

State the resolver, the lock-file rule, the registry URL, and the publishing UX (`{{project.name}} publish` or `{{project.name}} pkg push`). Cross-link to `STDLIB.md §1` — the inclusion-philosophy choice (small-core / batteries / curated) determines how much pressure lands on this package manager.

## 7. Build tool

How does {{project.name}} go from source files to runnable artefacts?

- **Invocation surface.** `{{project.name}} build` (the conventional command — Cargo, Go, Zig, Swift all use this), `{{project.name}} run` (build-then-execute), `{{project.name}} test` (build-then-run-tests with test-specific config). Subcommand discoverability — one binary with `--help` enumerating all subcommands — is the 2026 baseline; the multi-binary alternative (`{{project.name}}c` compiler + `{{project.name}}-pkg` package manager + `{{project.name}}-test` runner) is 1990s ergonomics and creates discovery friction.
- **Build cache.** **Content-addressed, incremental compilation, target-directory-based.** Cargo's `target/` directory + fingerprint-based invalidation is the 2026 reference. Each compilation unit's fingerprint is the hash of (source content, dependencies' fingerprints, compiler version, rustflags) — change any one and that unit's output is rebuilt; everything downstream is rebuilt transitively. The `sccache` ecosystem (Mozilla, now community-maintained) plugs in shared / distributed caches. Ship build caching from day one — without it, your CI times become a recruitment problem.
- **Incremental compilation reference architecture: `rust-analyzer`'s Salsa.** Salsa is a Rust library implementing **demand-driven incremental computation**: every "query" (parse this file, resolve this name, type-check this expression) is memoised; when an upstream input changes, only downstream queries that consumed it are invalidated. The model is from Adapton (Hammer et al., 2014); Salsa is the production-engineered descendant in Rust. The companion is **rowan** — a lossless concrete-syntax-tree representation where every byte of the original source (whitespace, comments, formatting) is preserved, enabling formatters and refactoring tools to round-trip without information loss. **If you are building a compiler with editor-grade incremental responsiveness, study Salsa + rowan as the prior art; do not reinvent the IR.**
- **Parallelism.** Modern build tools default to `-j$(nproc)` parallelism with a critical-path-aware scheduler. Cargo uses a job-graph executor; Go's `cmd/compile` parallelises at function granularity per package. State whether parallelism is enabled by default and how to disable it for debugging (`--jobs=1`).
- **Cross-compilation.** Can a Linux developer build a Windows binary without leaving their laptop? Rust's `--target=x86_64-pc-windows-msvc` (with `cargo zigbuild` as the 2026 universal-cross-compile-shortcut, using Zig's compiler-driver as a portable C/C++ toolchain), Go's `GOOS=windows GOARCH=amd64 go build`, Zig's native cross-compilation (the marquee feature). State the targets supported and the toolchain-installation story (`rustup target add ...` versus "it just works" Go-style).
- **Reproducible builds.** Bit-identical artefacts from identical inputs. Important for security audits (SLSA Level 3+ requires reproducibility), for distro packagers, and for supply-chain provenance. Rust ships `--remap-path-prefix`; Go has had reproducible builds since 1.10 (2018). Aspirational for v1; mandatory for any language targeting regulated industries by v2.

State the build tool's name (`{{project.name}}c`, `{{project.name}} build`, or integrated with the package manager), the cache directory layout, and the cross-compilation surface. Cross-link `CI_CD.md` for the CI-side invocation patterns.

## 8. Documentation generator

How do users publish API reference documentation?

- **First-party doc generator.** **`rustdoc`** is the 2026 reference: every Rust crate gets a generated HTML site (browse on `docs.rs`, free hosting), every doc comment is rendered with Markdown, every code example in a doc comment is *executed as a test* (`cargo test --doc`), every type cross-links to its definitions. Go's `go doc` + `pkg.go.dev` follows the same model with slightly less feature investment. The 2026 default: ship a doc generator with the toolchain, render Markdown in doc comments, execute code examples as tests.
- **Comment style.** `///` for outer doc comments on the next item, `//!` for inner doc comments on the enclosing item (Rust convention — increasingly common). `"""` triple-quoted docstrings (Python, immediately after `def` / `class`). `/** ... */` JavaDoc/JSDoc (Java, JS — verbose, supports structured tags like `@param`, `@returns`, `@throws`). Pick one and enforce it via formatter / linter.
- **Markdown vs reStructuredText vs custom.** **Markdown is the 2026 default** — CommonMark-compliant, GitHub-Flavoured-Markdown supported, every developer reads it, every editor renders it. reStructuredText (Sphinx, Python) is technically more powerful but the community has clearly trended toward Markdown over the last decade. Custom DSLs (JavaDoc tags, JSDoc `@`-tags) layered over Markdown are acceptable for structured metadata (`@param`, `@returns`).
- **Doc-tests.** Every code example in a doc comment is compiled and executed as part of `{{project.name}} test`. Rust's `cargo test --doc` runs all `///`-embedded examples; Python's `doctest` does the same for docstring examples. Doc-tests are the 2026 best-in-class — they fix the "documentation rots faster than code" problem at the root, because rotted docs become build failures. **Ship doc-tests at v1.0** if you can; retrofitting is far harder.
- **Hosting story.** Auto-publish to a community site (`docs.rs` for Rust, `pkg.go.dev` for Go, `hexdocs.pm` for Elixir / Erlang)? Or BYO-hosting (`pydoc` generates HTML you upload yourself)? The community-hosted model is sticky — once `docs.rs` existed, every new Rust crate inherited a documentation site for free, and the cultural expectation of "every public crate has rendered docs" took hold within months.
- **No doc generator.** Acceptable only for the smallest DSLs; everywhere else, "no doc generator" means users invent ad-hoc README conventions and the result is fragmentation.

State the comment syntax, the markup language, the doc-test execution rule, and the hosting story. Cross-link `STDLIB.md` — the stdlib's own documentation should be generated by this tool, eating the dogfood.

## 9. Test runner

How does {{project.name}} run tests?

- **Built-in (Rust / Go school).** `{{project.name}} test` is a first-class subcommand of the build tool, runs all tests in the project, prints pass/fail with a summary line. Rust: `#[test]` attribute marks a test function, `cargo test` discovers and runs them, output is "test result: ok. N passed; M failed; ..." Go: any function `TestXxx(t *testing.T)` in a `*_test.go` file is a test, `go test ./...` runs them all. **The built-in approach is the 2026 default** — discovery is automatic, no external runner to install, integration with build cache and CI is seamless, parallelism is built in, output format is uniform across all projects in the ecosystem.
- **External community standard (Python school).** Stdlib `unittest` exists but the community uses `pytest` (de facto since ~2013), and the gap between them is so wide that "use pytest" is the only sensible advice. The lesson: shipping a *worse* stdlib test runner alongside the language is *worse* than shipping nothing, because users now have to install + learn the better one anyway. **If you ship a built-in test runner, make it the best one; otherwise ship none and let the community pick.**
- **Assertion style.** `assert!(condition)` / `assert_eq!(a, b)` / `assert_matches!(value, Pattern)` macros (Rust) versus method-based `t.Equal(a, b)` / `t.NotNil(x)` (Go's `testify` package) versus expectation-style `expect(x).to.equal(y)` (BDD / Chai-style). Macros + good diff output ("expected `Foo { a: 1 }`, got `Foo { a: 2 }`" with field-by-field highlighting) are the 2026 best-in-class — `pretty_assertions` (Rust), Jest's snapshot diffs (JS).
- **Parallelism.** Tests run in parallel by default — Rust `cargo test` parallelises at the test-function level inside a binary plus at the binary level across crates; Go parallelises at the package level by default and at the test-function level when the user calls `t.Parallel()`. State whether tests are parallel by default, how to opt out (`--test-threads=1`), and whether shared state across tests is your problem (Go: yes, users must use `t.Parallel()` deliberately) or the runner's problem (Rust: defaults to parallel, isolates by process where possible).
- **Coverage.** Built-in coverage instrumentation versus external tool? Go ships `go test -cover` natively (since 1.2, 2013, with full source-based coverage via `-covermode=set/count/atomic`). Rust historically required `cargo-tarpaulin` or `cargo-llvm-cov` but is moving toward built-in (`cargo +nightly -Z source-based-code-coverage`, stabilising slowly). State whether coverage ships in the toolchain or via add-on.
- **Property-based + snapshot testing.** Property-based: Hypothesis (Python, de facto), `proptest` and `quickcheck` (Rust). Snapshot: `insta` (Rust), Jest snapshots (JS). Optional for stdlib in 2026, but increasingly an expected feature for serious languages — bug-finding power per developer-hour is an order of magnitude over example-based tests for the right problem domain. Cross-link `STDLIB.md §8c`.

State the discovery rule (`#[test]` attribute? `Test*` function names? a separate file convention?), the parallelism default, the coverage story, and the assertion library. Cross-link `TESTING_STRATEGY.md` for the *what to test* policy that consumes this tooling.
